# Simple native 5×5 app: research and implementation brief

Verified **2026-10-21** against official product pages, support documentation, release announcements, and publisher-owned npm packages. This note records the research brief written before implementation. See README.md and docs/verification.md for the delivered app and test results.

## Current stack: verified, not inferred from release schedules

- **Expo SDK 58**, announced October 15, 2026, includes **React Native 0.88**. The live npm `latest` tags resolve to **expo 58.0.17** and **react-native 0.88.0**; RN’s October 19 announcement specifies **React 19.3.0**. Use this compatible family, install Expo dependencies through `npx expo install`, and commit the resolved lockfile. [Expo SDK 58](https://expo.dev/changelog/sdk-58), [Expo package metadata](https://registry.npmjs.org/expo/latest), [RN package metadata](https://registry.npmjs.org/react-native/latest), [RN 0.88 announcement](https://reactnative.dev/blog/2026/10/19/react-native-0.88)
- **Source discrepancy:** Expo’s SDK index still stopped at 57 and RN’s versions index at 0.87 when checked. Their newer announcements and published packages supersede those stale indexes. Do not mistake scheduled dates, `next`, or nightly builds for stable releases. Expo’s upgrade guide now explicitly targets SDK 58 and recommends `npx expo install --fix` followed by `npx expo-doctor`. [Expo SDK index](https://expo.dev/sdk), [RN versions](https://reactnative.dev/versions), [Expo upgrade guide](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/)
- **“Expo UI only” should mean actual `@expo/ui` controls and layouts.** Expo UI became stable with SDK 56; its native implementations are Jetpack Compose on Android and SwiftUI on iOS. For this Android APK, use the Compose surface where it provides needed native controls, or universal components where their behavior fits. The current overview recommends `@expo/ui ~58.0.22`; resolve against the installed SDK rather than copying older examples. [Expo UI stable announcement](https://expo.dev/blog/expo-ui-stable-sdk-56), [Expo UI reference](https://docs.expo.dev/versions/latest/sdk/ui/)
- Every Compose component needs a `Host`. Use bounded screen/list dimensions: `matchContents` on a scrollable axis can crash because it supplies unbounded constraints. Use a development build during implementation and a standalone release APK for delivery; the SDK 58 announcement says store-distributed Expo Go will follow later. [Host reference](https://docs.expo.dev/versions/latest/sdk/ui/jetpack-compose/host/), [SDK 58 release notes](https://expo.dev/changelog/sdk-58)

## Product behavior and comparison

### StrongLifts: the closest behavior reference

- **Workout A:** squat 5×5, bench press 5×5, barbell row 5×5. **Workout B:** squat 5×5, overhead press 5×5, deadlift **1×5**. Alternate A/B each session, generally three times weekly with at least one rest day between sessions. Work sets use the same weight; displayed weight includes the bar. [Official quick start](https://stronglifts.com/stronglifts-5x5/workout-program/)
- **Counters:** one tap on an empty set circle logs the target reps; subsequent taps reduce 5→4→3→2→1→0→empty. Empty means unlogged/skipped; zero means an attempted lift with no completed reps. An unlogged set prevents an increase. Logging starts the rest timer; failed sets use a longer rest period. [Official phone logging instructions](https://support.stronglifts.com/article/212-log-sets)
- **Progression:** increase an exercise only after completing every prescribed work set; otherwise repeat its weight. Progress each lift independently. The app supports configurable increment size/frequency and defaults to a **10% deload after three consecutive unsuccessful sessions for that exercise**. Its support page gives +5 lb per successful squat workout as a default. The program guide also describes optional larger early deadlift jumps; these are not a universal fixed default. [App progression settings](https://support.stronglifts.com/article/71-progression), [Program progression](https://stronglifts.com/stronglifts-5x5/progress/)
- **Supporting features:** adjustable progression/deloads, return-from-break deload suggestions, automatic rest timer, warmup calculator, plates per side with configurable bars/plates, charts, calendar consistency and exercise history/records. Its warmup guidance starts light and adds weight toward the work weight rather than prescribing one fixed number of warmup sets at every load. [App features](https://stronglifts.com/app/), [Warmup calculator](https://support.stronglifts.com/article/87-warmup)

### Strong: flexible workout notebook

Strong emphasizes user-planned workouts, progress tracking, charts, export and device access rather than presenting a dedicated automatic 5×5 progression system. Its timer starts automatically after a completed set, defaults to two minutes, permits per-exercise settings and different warmup/work-set durations, and supports skip/manual adjustment. [Official product page](https://www.strong.app/), [Rest timer](https://help.strongapp.io/article/231-rest-timer)

Warmup calculation and plate calculation are PRO features. Warmups can be manually tagged and are excluded from metrics/charts; calculator formulas are customizable. Plate results describe plates on **each side**, account for bar weight, and have some Android/iPhone differences. Borrow the convenient tools without requiring subscription/account flows for this focused app. [Warmup calculator](https://help.strongapp.io/article/171-warm-up-calculator), [Plate calculator](https://help.strongapp.io/article/169-plate-calculator)

### Hevy: logging, progress and social features

Hevy’s official feature list includes routines, previous workout values, set types, notes, automatic rest, warmups, plates and extensive progress/social features. Its warmup calculator supports editable percentages/reps and rounding; settings identify it as PRO. Users can choose whether warmups count toward workout statistics. [Feature list](https://www.hevyapp.com/features/), [Warmups](https://www.hevyapp.com/features/warm-up-set-calculator/), [Workout preferences](https://help.hevyapp.com/hc/en-us/articles/33882110558743-Workout-Settings-Preferences-Timer-Warm-up-calculator-Plate-Calculator-Smart-Superset-Scrolling)

Its plate calculator supports custom bars/plates and reports the closest achievable weight when the target cannot be loaded. That explicit mismatch is valuable for a home gym. The reviewed Strong/Hevy pages establish general logging tools, not evidence that they automatically implement StrongLifts’ success/failure/deload rules. [Hevy plate calculator](https://www.hevyapp.com/features/weight-plate-calculator/)

## Recommended focused offline-first scope

The following are **design recommendations**, not claims of exact parity with any product:

1. **Today / Workout / History / Settings:** configure kg/lb, starting weights, bar and plates; show the next A/B session and last results. Three exercise cards with large native set counters form the central screen. A rest-day suggestion must not block logging.
2. **Fast logging with correction:** implement the documented empty→5→4→…→0→empty cycle; offer an explicit native edit/clear action so users need not discover repeated taps. Keep unlogged, attempted-zero, warmup and completed states distinct. Autosave every change and resume an unfinished workout after restart.
3. **Deterministic progression:** per-lift editable increment (initial proposal: +2.5 kg / +5 lb), repeat after incomplete work sets, propose 10% reduction after three unsuccessful exercise exposures. Explain the next weight and permit overrides. Count only finalized, attempted exercise exposures toward failure streaks; fully skipped exercises do not add failures. Reset after success or accepted deload. These last details are deliberate local rules, not verified StrongLifts internals.
4. **Reliable completion:** finalize a session once, atomically; advance A/B only on finalization, never on opening or discarding it. Store the weight actually lifted and the progression decision separately. History corrections/deletions must follow a documented recalculation policy and never silently apply progression twice.
5. **Rest:** auto-start on a newly logged set; proposed editable presets of 90 seconds, 3 minutes and 5 minutes, with longer rest after failure, +30 seconds and skip. Persist a deadline and recompute remaining time on foreground/relaunch; do not depend on an uninterrupted JavaScript interval. Editing reps must update one timer, not create duplicate alerts.
6. **Warmups:** optional, editable lighter sets based on the work weight and available equipment. Round to loadable weights, remove duplicate steps, never exceed the work weight, and handle an empty-bar work weight. Separate them from work-set progression and records. A transparent editable template is preferable to claiming to reproduce StrongLifts’ full algorithm.
7. **Plates:** show `(total − bar) / 2` and exact plates per side; support bar weight, plate denominations and available pairs. Explicitly report below-bar, impossible and insufficient-inventory targets; offer a loadable alternative without silently changing the workout. Use fixed-precision weight arithmetic and preserve values when switching units.
8. **History and ownership:** dated session list/calendar, set-by-set detail, notes, per-lift weight history and simple best successful work-set records. Include backup export/import with schema validation and a clear replace/merge choice; CSV is useful for reading, versioned JSON for restoration. All core flows must work in airplane mode without sign-in.

Defer social feeds, coaching, body photos, exercise video libraries, wearables, subscriptions and arbitrary program builders. A complete 5×5 tool can remain small while covering the entire training loop above.

## Official engineering guidance and its implications

- **Performance:** RN recommends measuring release builds because development mode has substantial overhead; avoid expensive work in tap handlers and excessive logging. Keep the ticking timer’s render updates local, query history in bounded pages, and use native lazy/recycling lists for long history. These last choices apply the guidance to this app. [RN performance overview](https://reactnative.dev/docs/performance), [Expo UI list additions in SDK 58](https://expo.dev/changelog/sdk-58)
- **Accessibility:** RN documents labels, roles, state/value and platform differences. For Compose controls use Expo UI’s native semantics rather than assuming RN accessibility props reach through `Host`; `semantics({ contentDescription })` and the `testID` modifier are documented. Announce e.g. “Squat, set 2 of 5, 3 of 5 reps,” preserve visible failure text as well as color, support large fonts, and test TalkBack traversal/dialog focus. Android recommends at least **48 dp** touch targets; five counters must wrap rather than shrink on narrow or enlarged-text screens. [RN accessibility](https://reactnative.dev/docs/accessibility), [Expo Compose modifiers](https://docs.expo.dev/versions/latest/sdk/ui/jetpack-compose/modifiers/), [Android accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)
- **Storage:** Expo identifies SQLite as persistent across restarts, AsyncStorage as unencrypted key/value storage suited to small preferences, and SecureStore as storage for small secrets. Recommend **`expo-sqlite`** for workout/set/history data and settings to avoid unnecessary storage dependencies. Use migrations, foreign keys, WAL, bound parameters/prepared statements, and atomic finalization; Expo warns that `execAsync` does not escape inputs and ordinary async transactions can include interleaved queries. Use `withExclusiveTransactionAsync` where transaction scope must be isolated. [Storage choices](https://docs.expo.dev/develop/user-interface/store-data/), [SQLite API and transaction guidance](https://docs.expo.dev/versions/latest/sdk/sqlite/)
- **Notifications:** use local scheduled notifications for optional rest alerts. Android 13+ requires notification permission; exact-time scheduling has additional Android 12+ permission requirements, with Android 14+ denying exact-alarm access by default for new installs. Verify the actual APK’s permission-granted and permission-denied behavior. Keep the in-app deadline authoritative and describe best-effort alerts honestly if exact scheduling is unavailable. [Expo notifications](https://docs.expo.dev/versions/latest/sdk/notifications/)
- **Testing:** Expo recommends Jest with `jest-expo` and React Native Testing Library; avoid the deprecated standalone `react-test-renderer` approach. RN explicitly says Node component tests do not exercise backing Android/iOS code. Compose controls therefore require installed-app interaction coverage even when mocked JS tests pass. Expo documents Maestro E2E workflows. [Expo unit tests](https://docs.expo.dev/develop/unit-testing/), [RN testing overview](https://reactnative.dev/docs/testing-overview), [Expo Maestro workflow](https://docs.expo.dev/eas/workflows/examples/e2e-tests/)

## Acceptance evidence for a feature-complete tested APK

- **Logic tests:** A/B alternation and deadlift 1×5; all-success versus partial/zero/skipped sets; independent lift progression; third failure/deload/reset; unit precision; plate inventory/impossible targets; warmups below work weight; history edits and repeated finalization.
- **Persistence tests on native storage:** restart mid-workout, complete/reopen, export/import round trip, migration without lost sets, and no duplicate progression on repeated finish taps.
- **Installed Android E2E:** finish A then B; edit a failure; inspect next weights, warmups, plates and history; background/reopen during rest; verify alert permission denial; repeat core flow in airplane mode. Check large fonts, TalkBack and a long history on a representative device/emulator.
- **Deliverable:** a standalone, signed release **`.apk`**, installed and smoke-tested with Metro stopped. EAS normally produces an AAB for Android store distribution; set an APK profile such as `android.buildType: "apk"` or use an APK-producing release Gradle command. Record artifact path/hash, dependency versions, device/API, commands and passed/failed scenarios. A successful bundle or mocked test suite alone does not establish a tested APK. [Official APK build guide](https://docs.expo.dev/build-reference/apk/)

Product pages establish advertised behavior, not independent hands-on verification or permanent free/paid entitlements. Exact StrongLifts warmup formulas and all historical-edit effects are not established by these sources; implement explicit, tested local policies.
